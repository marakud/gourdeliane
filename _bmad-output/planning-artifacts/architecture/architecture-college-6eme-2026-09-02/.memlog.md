- (version) Next.js 16 (LTS actuel, bundle React 19.2) verifie sur nextjs.org/blog, sept 2026.
- (version) Prisma ORM 7.8.0 stable retenu plutot que Prisma 8 (encore RC en aout 2026). Prisma 7 est Rust-free (runtime TS pur), pertinent pour Vercel serverless (fini les soucis de binaire engine).
- (version) Tailwind CSS 4.3 (config CSS-first, variables OKLCH) verifie compatible avec shadcn/ui et Next 16 en 2026.
- (decision) Framer Motion a ete renomme Motion -- paquet npm a installer: 'motion' (framer-motion reste un alias deprecated). Version verifiee: 13.2.x.
- (decision) PWA: next-pwa n'est plus maintenu. Utiliser Serwist (@serwist/next), successeur recommande et integre officiellement dans la doc Next.js pour l'App Router. Corrige la mention 'next-pwa' de l'addendum du brief.
- (constraint) Vercel Hobby (gratuit): cron jobs limites a 1 execution/jour par job, precision garantie seulement a +/-59min (pas a la minute pres). Impact FR-10: les 3 rappels (soir/matin/retour) restent faisables (3 cron jobs distincts, 100 autorises/projet) mais l'heure exacte configuree par l'utilisateur ne sera pas respectee a la minute pres sur le plan gratuit -- a accepter comme limite du palier gratuit ou upgrader Vercel Pro si la precision devient un vrai probleme a l'usage.
- (decision) AD-10 (correction du brief addendum): Supabase Postgres est OBLIGATOIRE en production, pas une alternative interchangeable a SQLite -- le systeme de fichiers de Vercel serverless est ephemere, SQLite n'y persiste pas les ecritures entre invocations. SQLite reste utilisable uniquement pour le dev local via le multi-provider Prisma.
- (decision) AD-1 Paradigme: architecture en couches avec noyau de domaine isole (domain/ pur TypeScript, zero dependance Next.js/Prisma) -- app/ (presentation) -> actions/ (Server Actions, seule frontiere de mutation) -> domain/ + data/ (Prisma). Empeche la logique de derivation (checklist, streak) d'etre dupliquee/divergente entre composants UI.
- (decision) AD-2: les blocs Sac et Revisions (FR-3, FR-19) sont des vues DERIVEES calculees a la lecture depuis EDT+Subject+SubjectItem+Devoir -- jamais persistees comme lignes generees. Empeche la derive entre une copie stockee et l'EDT reel.
- (decision) AD-3: l'etat de coche par item persiste dans une table generique keyee par (date, checklistType, sourceType, sourceId) -- jamais par le libelle affiche. Permet le recalcul en direct (FR-3/FR-19) sans perdre l'etat coche quand un libelle est edite, et exclut naturellement les items retires sans purge explicite necessaire.
- (decision) AD-4: le jour scolaire (aujourd'hui/demain, limites du soir) est calcule cote serveur dans un fuseau fixe Europe/Paris, jamais depuis l'heure locale de l'appareil client. Empeche une bascule de moment incoherente entre telephone et tablette ou pres de minuit.
- (decision) AD-5: le Streak (FR-13) est derive en remontant un journal DayCompletion (une ligne par jour scolaire, calculee a partir des ChecklistItemState), jamais un compteur mutable incremente directement par une action client. Les Badges (FR-14) sont une fonction pure du meilleur streak (seuils), aucune table d'unlock separee. Empeche desynchronisation/double-incrementation.
- (decision) AD-6: l'index de couleur d'une matiere (subject-tag DESIGN.md) est assigne une fois a la creation et persiste, jamais recalcule depuis l'ordre courant -- la suppression d'une matiere ne doit pas decaler les couleurs des autres.
- (decision) AD-7: toute mutation (cocher un item, ajouter/editer un devoir, editer l'EDT ou les objets par matiere) passe exclusivement par des Server Actions -- pas d'API REST separee qui dupliquerait la validation/regles metier.
- (decision) AD-8: un Devoir persiste independamment du cycle de reinitialisation quotidien (contrairement aux ChecklistItemState de Sac/Matin/Retour/Revisions) -- pas de job de nettoyage necessaire, le 'reset' est un effet naturel du recalcul par date (AD-2/AD-3), pas une purge active.
- (decision) AD-9: la programmation des notifications (FR-10) tourne cote serveur (3 Vercel Cron Jobs distincts, un par moment) qui invoquent une route de dispatch push -- jamais un timer cote client (peu fiable app fermee/arriere-plan). Le repli visuel in-app (FR-11) se calcule depuis l'etat des items en attente a l'ouverture/premier plan de l'app, independamment de toute confirmation de reception push.
- (decision) Convention de nommage: identifiants de code (entites, fichiers) en anglais (Subject, Homework, ChecklistItemState, DayCompletion) meme si le domaine/PRD est en francais -- evite un melange bilingue incoherent dans le code.
- (decision) Utilisateur unique v1: un seul User (identifiant simple, ex. PIN ou lien magique -- mecanisme exact laisse a l'implementation) plutot qu'un systeme de comptes complet. Toutes les entites sont neanmoins scopees par userId des la conception pour ne pas re-architecturer si vue parent/multi-enfant arrivent plus tard.
- (question) Alternance de semaines A/B pour l'EDT (PRD question ouverte #1) non tranchee -- l'architecture part sur un EDT hebdomadaire fixe (ScheduleSlot sans notion de semaine A/B). Si l'alternance existe reellement, ScheduleSlot devra gagner un champ weekParity -- changement localise, pas structurel.
- (direction) Deferred: Vue Parent complete, integration Pronote/pawnote, multi-enfant/multi-profil, calendrier scolaire officiel automatise, environnement de staging/CI (projet perso, un seul environnement de prod), suite de tests automatises detaillee (laissee au stade dev/build), i18n (francais uniquement, fixe).
- (event) spine finalized
- (decision) Auto-revue adversariale: risque identifie ou l'UI pourrait recalculer independamment la completude d'un moment (pour declencher la celebration de facon optimiste) et diverger de DayCompletion cote serveur. Convention ajoutee: l'UI affiche toujours l'etat retourne par la Server Action, jamais un calcul local independant.
